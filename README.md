# coherence-harness

A commit-time coherence harness for multi-agent and tool-using workflows.

The idea, from Heng (2026): each agent can make a locally valid decision
and the team can still produce an invalid result, because the failure is
in shared state, not in intelligence. Models propose; the harness owns
shared state and governs commit. This library implements that harness in
dependency-free Python: proposals are validated against global
invariants and applied atomically, or rejected with nothing changed.

It also implements verified-failure-only effort escalation from Sun et
al. (2026): start at the lowest reasoning effort and escalate only when
a verifier reports failure, instead of paying maximum effort on every
task.

No LLM calls, no API keys, no GPU. Every measurement below comes from
seeded simulations in this repository (`results/experiment.json`,
regenerated by `scripts/run_scenarios.py`).

## Why this is useful

Anyone running several agents against one budget, one document, or one
set of facts hits the same failure modes:

- Two agents each check "enough budget remains" and jointly overspend.
- One agent writes `250 cm`, another writes `2.5 m`, and a naive
  checker calls it a conflict — or one writes `250` meaning inches.
- Two agents edit the same entity under different names
  (`total_cost` vs `cost_total`) and the merge silently picks one.
- An agent works from a stale snapshot and overwrites a newer update.
- A maximum-effort call is bought for a task the cheapest effort
  already solves.

`coherence-harness` gives those checks one home, at commit time, with
an audit trail. Drop the `Harness` in front of your workers' tool
calls: workers return proposals, the harness accepts or rejects them,
and every decision is recorded.

## Quickstart

```bash
python -m venv .venv && . .venv/bin/activate
pip install pytest          # tests only; the library itself has no dependencies
PYTHONPATH=src python -m coherence.cli demo
PYTHONPATH=src python -m coherence.cli scenario team-bench
PYTHONPATH=src python -m coherence.cli compare
```

Use it as a library:

```python
from coherence import Harness, Intent, Proposal, Quantity
from coherence.budgets import Budget, Ledger
from coherence.state import VersionedStore

harness = Harness(store=VersionedStore(), ledger=Ledger())
harness.ledger.add_budget(Budget("calls", Quantity(100, "calls")))

proposal = Proposal("worker-0", [Intent(
    kind="spend", key="work",
    amount=Quantity(60, "calls"), unit="calls", budget="calls")])
result = harness.commit(proposal)
assert result.accepted  # 60 of 100 spent

result = harness.commit(Proposal("worker-1", [Intent(
    kind="spend", key="work",
    amount=Quantity(60, "calls"), unit="calls", budget="calls")]))
assert not result.accepted  # BUDGET_EXCEEDED; nothing applied
```

Audit a proposal file without writing code:

```bash
PYTHONPATH=src python -m coherence.cli audit examples/proposal.json
```

## What the harness checks

| Check | What it catches |
|---|---|
| `budget_cap` | A proposal whose total spend exceeds the remaining budget |
| `no_double_spend` | One reservation id used twice in a proposal |
| `unit_consistency` | Declared unit and amount unit in different dimensions |
| `no_conflicting_write` | One key written with two values in one proposal |
| `version_freshness` | A write based on a stale version (compare-and-swap) |
| aliasing / gluing | Aliased names for one entity carrying different values; local views that disagree on a shared key |

Commit modes: `blind` applies without checks (the baseline),
`visible` checks but only warns and still applies (a live count with
no enforcement), `enforce` rejects violations atomically. The default
is `enforce`.

Units are dimension-checked and canonicalised: `250 cm` and `2.5 m`
are the same quantity, while `1 m + 1 USD` raises
`DimensionMismatch`. Currency conversion uses caller-supplied FX
rates; the built-in defaults are fixed illustrative rates, not live
rates.

Effort escalation (`coherence.escalation`) runs five levels
(low 1x, medium 3x, high 9x, xhigh 21x, max 42x — cost multipliers are
parameters anchored to the 42x ratio reported by Sun et al., not
measurements of a live API) and escalates only on verified failure.

## Measured results

All numbers below are from `scripts/run_scenarios.py` (seeds 0–4 for
the harness scenarios, seeds 0 and 42 for the escalation comparison,
200 tasks each) and are recorded in `results/measured.json`. They are
simulation measurements, not the numbers from the cited papers.

### Shared budget (TeamBench analogue)

Five workers each spend 30 from a shared cap of 100 (joint total 150).
Five runs per mode:

| Mode | Runs over cap | Mean total spent |
|---|---:|---:|
| blind | 5 / 5 | 150.0 |
| visible (live count, no enforcement) | 5 / 5 | 150.0 |
| enforce (commit-time) | 0 / 5 | 90.0 |

Seeing the live count did not stop overspending; only commit
enforcement did. Under enforcement exactly 3 of 5 spends are accepted
in every run (3 × 30 = 90; a fourth would exceed the cap).

### Hidden vs visible deciding fact (observation aliasing)

40 revision questions, 3 options, 3 seeds per setting:

| Setting | Mean accuracy |
|---|---:|
| Deciding fact hidden | 0.358 (43 / 120) |
| Deciding fact visible in the harness store | 1.000 (120 / 120) |

Hidden accuracy sits near chance (1/3), as the impossibility result
predicts: no local reasoning recovers a fact the worker cannot see.

### Silent revert

An external change silently reverts the stored config. A checker
holding a stale snapshot scores 0.000; the harness, which re-reads
current state at check time, scores 1.000 (5 runs each).

### Unit / alias gluing

Views writing `250 cm` and `2.5 m` for the same entity glue with 0
disagreements across 5 runs. Views writing `250 cm` and `3.0 m`
produce 1 disagreement per run (5 total).

### Effort escalation (simulated tasks, verifier ground truth)

| Policy | Seed 0 successes | Seed 0 total cost | Seed 0 cost / success |
|---|---:|---:|---:|
| fixed low | 86 / 200 | 200 | 2.33 |
| fixed max | 152 / 200 | 8400 | 55.26 |
| escalate on verified failure | 200 / 200 | 2219 | 11.10 |
| oracle (cheapest solving level) | 200 / 200 | 1391 | 6.96 |

Seed 42 repeats the pattern: escalate 200 / 200 at total cost 2483,
fixed max 167 / 200 at 8400. Escalation cost 73.6% less than fixed
max on seed 0 (70.4% less on seed 42) while solving more tasks.
Fixed max fails tasks the escalation solves, because in this
simulation — as in Sun et al. — higher effort does not monotonically
preserve lower-effort successes.

## Tests

64 tests, all passing, in a fresh virtualenv (see `tests/`):

```bash
python -m venv .venv && . .venv/bin/activate
pip install pytest
PYTHONPATH=src python -m pytest -q
# 64 passed
```

The suite covers every module (units, versioned store, budget
ledger, invariants, harness commit modes, aliasing/gluing,
escalation), CLI behaviour as a subprocess, and end-to-end
scenarios. Reproducibility was checked three ways: the experiment
script run twice produces byte-identical output apart from runtime;
the same run from a clean copy of the tree (no results directory)
produces identical output; and the escalation comparison is identical
for a repeated seed. Two bugs found by the suite during development
were fixed before release: blind/visible modes leaked the ledger cap
check, and unit canonicalisation raised before the invariant could
report the mismatch.

## Project layout

```

  units.py       dimension-checked quantities and conversion
  state.py       versioned store, compare-and-swap, audit history
  budgets.py     atomic reserve / commit / release ledger
  invariants.py  commit-time invariants
  harness.py     propose / commit, aliasing, gluing, audit trail
  workers.py     deterministic simulated workers

  cli.py         audit / scenario / compare / demo commands
scripts/
  run_scenarios.py   regenerate results/experiment.json and measured.json
  demo.py            team-budget scenario in all three commit modes
config/default.yaml  budgets, units, FX rates, effort levels
examples/            proposal.json and scenario.yaml
```

## Limitations, stated honestly

- Workers are simulated policies, not LLMs. The scenarios measure the
  harness, not model behaviour; the paper numbers in
  `docs/RESEARCH.md` are the papers', and the numbers in this README
  are this simulation's.
- Cost multipliers in the escalation module are parameters, not
  measurements from any provider's API. Do not quote them as such.
- FX rates are fixed illustrative values. Supply live rates before
  any real-money use.
- The harness is in-process and single-threaded. For concurrent
  workers across processes, put the store and ledger behind a
  database with real transactions; the invariant and commit
  semantics here are the specification to implement there.
- Scale-up path: the same commit semantics apply unchanged if
  proposals come from real agents (LangChain / AutoGen / custom
  tool loops) — replace `workers.py` with adapters that turn tool
  calls into `Intent`s, and keep the harness as the only writer to
  shared state. GPU work is not involved; this is a coordination
  library, not a training framework.
